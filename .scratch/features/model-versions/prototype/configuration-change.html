Configuration eras and model versions PROTOTYPE, throwaway

Tickets "Hypotheses for what one configuration change is" and "What should a human-readable change log look like". Round 3, after the maintainer's reactions of 2026-10-22. Real data: the Boiler rename (2026-08-13) and the v6 → v7 change (2026-10-05) from syslab/conf, the Java displet, the overview figure and our curated data; feature-branch logging, future steps and model numbers are illustrative.

The question. Does this two-level structure hold up?
  1. Configuration era: a time period marked by one major configuration change (typically a new switchboard; also planned equipment becoming built). The major change is announced by a new overview figure, evidenced by new data headers (often while the node runs a feature-branch config) and materialized by hardware.xml in master: all of that belongs to the same era. Minor changes (renames, bays, cables) are logged inside the era. Eras are named after the figure: E6, E7, E7b (a further era under the same figure).
  2. One base model per era, improved over the era's life and published as model versions 7.1, 7.2, ...; scenario models derived from a base version (7.2/summer-2027). Each records the changes it accommodates, where it was validated, and optional validity periods. The base model applies anywhere in the era, with fewer guarantees outside its validations.
Authority for names: hardware.xml once it exists; before that, the names in the data headers are provisional. Figure-only equipment is planned. Lag and label mix-ups are flagged, not corrected.
