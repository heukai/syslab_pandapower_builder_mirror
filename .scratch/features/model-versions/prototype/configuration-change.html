Configuration eras and model versions PROTOTYPE, throwaway

Tickets "Hypotheses for what one configuration change is" and "What should a human-readable change log look like". Round 2, after the maintainer's reaction of 2026-10-22. Real data: the Boiler rename (2026-08-13) and the v6 → v7 change (2026-10-05) as seen in syslab/conf, the Java displet, the overview figure, the FTP headers and our curated data; future steps and model numbers are illustrative.

The question. Is this the right two-level structure for talking about the grid over time?
  1. Configuration era (from H3): a snapshot of the grid. A new era opens only when hardware.xml brings a new switchboard (a new node), or when planned equipment becomes built. Everything else (renames, bay edits, a new cable) is an element edit logged inside the era. A new figure version is logged as an indicator; it names the era but does not open one on its own.
  2. Model version: many per era (improvements, scenarios), numbered inside their era (7.1, 7.2). Each carries the changes it accommodates, the instances it was validated on, and optional validity periods inside its era. Models change at lab events (yearly experiments), not continuously.
Era names follow the figure: the era in force with figure v7 is E7; a further era while the figure is still v7 is E7b. Rules applied: hardware.xml is authoritative for switchboards, bays and breakers; curated or declared data for cables; Java and figure are evidence; figure-only equipment is planned; lag and label mix-ups are flagged, not corrected.
